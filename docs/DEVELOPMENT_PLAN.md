# CreoBoard — план разработки

Принципы:

- Один шаг = одна ветка = один PR с тестами. Каждый коммит маленький и по одной теме.
- PR вливается только при зелёном CI. Merge делает человек.
- **Деплой запускаем рано** (шаг 2, «ходячий скелет»), чтобы проблемы сервера и сети вылезли в первые часы, а не в последние.
- Оценки учитывают работу человека вместе с Claude Code. Если время поджимает, см. раздел «Что резать».

## Шаблон запроса к Claude Code

```
Прочитай CLAUDE.md и docs/ARCHITECTURE.md. Выполни шаг N из docs/DEVELOPMENT_PLAN.md.
Сначала предложи план (не пиши код), затем после моего подтверждения реализуй
с тестами в ветке feat/N-slug, делай небольшие коммиты, перед PR запусти make ci (пока нет frontend/ и prod-compose: make ci-back), в конце открой PR.
```

## Детали шагов

### 0. Каркас репозитория
- Положить `CLAUDE.md`, `.claude/`, `docs/`, `README.md`, `.env.example`.
- `.gitignore`, `.gitattributes` (`* text=auto eol=lf`), `.editorconfig`.
- `Makefile` по образцу ваших `django-dds-manager` и `FastAPI-QA-Service`: блок docker compose, `lint`, `test`, `lt`, `req`, плюс цели Django, frontend, `ci`, `sync`, `rebase`.
- `pre-commit` (ruff, gitleaks, проверка больших файлов).
- Шаблон PR с чек-листом DoD.
- Защита `main` в GitHub: PR обязателен, статус-проверки обязательны, прямой push запрещён.
- **Готово, когда:** репозиторий создан, ветка защищена, первый PR влит.

### 1. Каркас backend
- Poetry (`backend/pyproject.toml`, группа `dev`), экспорт зависимостей `make req`.
- Django-проект с настройками `base/dev/prod`, django-environ.
- Подключение к PostgreSQL, `docker/docker-compose.yml` для локальной БД (`make db`).
- Приложения-пустышки, минимальная `users.User(AbstractUser)` и `AUTH_USER_MODEL` (чтобы шаг 2 не применил миграции со стандартным `auth.User`; поле `role` добавит шаг 3), `GET /api/v1/health/`, drf-spectacular.
- `backend/Dockerfile` (multi-stage, не root).
- `ci.yml` (backend-часть с Postgres-сервисом, вызывает `make lint`, `make check`, `make test`) и `security.yml` (gitleaks, pip-audit, bandit).
- Dependabot.
- **Готово, когда:** CI зелёный, `check --deploy` проходит с prod-настройками.

### 2. Ходячий скелет деплоя
- `docker/docker-compose.prod.yml`, `docker/nginx.conf`, временная страница-заглушка вместо SPA, проверка `make config` в CI.
- `deploy.yml`: сборка образов, push в GHCR, SSH, `compose pull/up`, healthcheck, откат.
- Настройка Elestio и секретов GitHub по `docs/SETUP_WINDOWS.md`.
- `limit_req` для `/api/v1/auth/login/` в `docker/nginx.conf` (отдельная зона, `burst`, ответ 429) — это строгий лимит, так как лимит приложения из-за 3 воркеров gunicorn до 3 раз выше номинала. **Проверка:** серия быстрых POST на login через nginx контейнера `web` даёт 429.
- Проверить `DJANGO_NUM_PROXIES` (по умолчанию в prod 2: nginx Elestio и nginx `web`): реальный IP клиента, а не подделанный `X-Forwarded-For`, попадает в throttle.
- Загрузка файлов (требования шага 6): `client_max_body_size` в `docker/nginx.conf` для `/api/` не меньше `MAX_UPLOAD_MB` + 1 МБ (передать `MAX_UPLOAD_MB` в compose), ответ nginx на файл больше лимита 413 (**проверка:** запрос с телом больше лимита); лимит nginx Elestio не меньше; том `media` смонтировать в `/app/media` с владельцем uid 10001; каталог `/media/` через nginx не отдавать; таймауты прокси и `GUNICORN_TIMEOUT` (60 с) согласовать с загрузкой файла максимального размера.
- Тело запроса к API, кроме загрузок, ограничить в nginx небольшим лимитом (замечание ревью шага 5 про JSON-тело); в приложении этот лимит уже задан `DATA_UPLOAD_MAX_MEMORY_SIZE`.
- **Готово, когда:** по HTTPS-адресу сервиса открывается заглушка и отвечает `/api/v1/health/`.

### 3. Аутентификация
- Поле `role` у `User` (модель создана в шаге 1), Argon2, валидаторы паролей.
- `GET /auth/csrf/`, `POST /auth/login/`, `POST /auth/logout/`, `GET /auth/me/`.
- Throttle на login, настройка cookie и CSRF.
- Тесты: успешный вход, неверный пароль, лимит попыток, выход, CSRF-защита, неактивный пользователь.

### 4. Задачи
- Модели `Task`, `TaskEvent` и миграции с индексами и ограничениями.
- CRUD: создание (buyer), список с фильтрами и пагинацией, карточка, правка в статусе «Новые».
- Видимость по ролям через `get_queryset`.
- События `created` и `updated`.
- Эндпоинт `GET /tasks/{id}/events/` (история задачи): видимость как у задачи, чужая задача даёт 404.
- Тесты: матрица прав из ARCHITECTURE (по ролям, чужие задачи дают 404), валидация полей, история (401, 404, видимость).

### 5. Переходы статусов
- `services.py`: `take`, `submit`, `accept`, `request_revision`.
- Атомарность и блокировки, события, временные метки, `revision_count`.
- `allowed_actions` в сериализаторе, эндпоинты действий.
- Тесты: каждый допустимый переход, каждый недопустимый, чужой пользователь, **гонка двух креативщиков на одну задачу** (конкурентный тест), неизменяемость `TaskEvent`.

### 6. Референсы и вложения
- Модели и эндпоинты, валидация расширения и сигнатуры, лимит размера, случайные имена.
- Скачивание через авторизованный эндпоинт (вложения и файлы-референсы).
- `submit` требует вложение текущего раунда (заменяет `TODO` шага 5, логика переходов не меняется).
- Лимиты запросов Django согласованы с `MAX_UPLOAD_MB`; требование к `client_max_body_size` nginx записано в шаге 2.
- Тесты: запрещённое расширение, подмена расширения, превышение размера, скачивание без прав, `submit` без вложения.

### 7. AI-расходы
- `AIService`, `AIUsage`, эндпоинты, правила по статусам, `round` из `revision_count`.
- События `ai_usage_*`.
- Тесты: права, отрицательные значения, раунды после правок, `Decimal`-точность.

### 8. Аналитика
- Эндпоинты `summary`, `workload`, `durations`, `ai-costs` с фильтром по периоду.
- Метрики по определениям из ARCHITECTURE.
- Тесты на фиксированном наборе данных с известными ответами, доступ только для lead, проверка числа SQL-запросов.

### 9. Демо-данные и админка
- `seed_demo` (идемпотентная, только при `DEMO_MODE=1`).
- Админка: пользователи, справочник AI-сервисов, `TaskEvent` только для чтения, группа «Lead».
- Тест: повторный запуск seed не дублирует данные, без `DEMO_MODE` команда отказывается работать.

### 10. Каркас frontend
- Vite + React + TS, Tailwind, shadcn/ui, роутинг, защищённые маршруты.
- API-клиент с CSRF-заголовком, типы из OpenAPI.
- Страница входа, layout с учётом роли.
- Dockerfile фронтенда в образе `web`, замена заглушки.
- CI: eslint, tsc, vitest, build.

### 11. Kanban и задачи
- Доска из 5 колонок, карточки с приоритетом, дедлайном и просрочкой.
- Drag-and-drop по `allowed_actions`, откат при ошибке сервера.
- Форма создания ТЗ, карточка задачи, действия (взять, сдать, принять, правки с комментарием).
- Фильтры.

### 12. Детали и дашборд
- Вложения и референсы в карточке, форма AI-расходов, лента истории.
- Дашборд руководителя: счётчики, загрузка, средние времена, просрочки, AI-расходы по сервисам и исполнителям (Recharts).
- Состояния загрузки, ошибки, пустые состояния, адаптивность.

### 13. Укрепление и документация
- 1–2 e2e-сценария Playwright (полный цикл задачи).
- Проверка по чек-листу безопасности из ARCHITECTURE, `pip-audit`, `npm audit`, Trivy.
- Финальный README (демо-ссылка, пользователи), `docs/AI_WORKFLOW.md`.
- Доступ lead к `/api/v1/schema/` и `/api/v1/docs/` в prod: permission `IsLead`, CSP для Swagger UI, тесты 401/403/200, обновить тест, который сейчас ожидает 404 без DEBUG.
- Проверка, что в рабочем деплое `DEBUG=0`, секреты свои, бэкап настроен.

### 14. Бонус: уведомления
Только после готового основного проекта. Источник событий уже есть (`TaskEvent`). Вариант: Telegram-бот, отправка по событиям `taken`, `submitted`, `accepted`, `revision_requested` и по приближающимся дедлайнам.

## Что резать, если не успеваем (по порядку)

1. e2e-тесты Playwright (оставить unit и API-тесты).
2. Фильтры доски на фронтенде.
3. Графики на дашборде (оставить таблицы и счётчики).
4. Редактирование задачи в статусе «Новые».

**Не резать:** тесты прав, атомарность «взять», журнал событий, шаги безопасности и деплой.
