## 2. Организация агентов

Работа с Claude Code построена как конвейер на одного человека и нескольких специализированных субагентов. У каждого субагента свой контекст и свои права (файлы `.claude/agents/`).

| Агент | Роль | Права |
|---|---|---|
| `backend-dev` | Реализация Django/DRF-кода по шагу плана | чтение, запись, bash |
| `frontend-dev` | Реализация React-интерфейса | чтение, запись, bash |
| `test-writer` | Негативные и граничные тесты: права, IDOR, гонки, переходы статусов | чтение, запись, bash |
| `security-reviewer` | Независимое ревью каждого PR по чек-листу безопасности | только чтение |

Схема одного шага:

```
Человек: ставит задачу шага ──► plan mode: план
        │                               │
        │ утверждает план               ▼
        ▼                     backend-dev / frontend-dev: код + коммиты
   test-writer: тесты ◄───────────────┘
        │
        ▼
 security-reviewer: ревью diff ──► исправления
        │
        ▼
 PR ──► GitHub Actions (тесты, линтеры, сканеры) ──► человек смотрит diff и делает merge
```

Правила, которые удерживали качество:

- Общие правила проекта зафиксированы в `CLAUDE.md`; после каждой ошибки AI в файл добавлялось правило.
- Ни один шаг не начинался без утверждённого плана.
- Merge в `main` делал только человек после зелёного CI и просмотра diff.
- Секреты не передавались агентам: чтение `.env` запрещено настройками, деплой выполняют GitHub Actions.

## 8. Осознанные отступления от плана

| Решение | Что решили и почему |
|---|---|
| Кастомная модель `User` уже в шаге 1 | Минимальный `users.User(AbstractUser)` создан в шаге 1, поле `role` добавлено в шаге 3. Так `AUTH_USER_MODEL` не меняется после первых миграций, а шаг 2 не применит миграции со стандартным `auth.User` (обоснование записано в `DEVELOPMENT_PLAN.md`, шаг 1). |
| Шаг 3 выполнен раньше шага 2 | Аутентификация не зависит от деплоя. Всё, что зависит от сервера, внесено в шаг 2 явными пунктами: `limit_req` на login в `docker/nginx.conf` с проверкой и проверка `DJANGO_NUM_PROXIES`. |
| Throttle login: `LocMemCache` плюс nginx `limit_req` | Выбор сделан пользователем из двух вариантов (второй — `DatabaseCache`). `LocMemCache` не требует новых таблиц и шагов деплоя, но счётчики локальны для процесса, поэтому при 3 воркерах gunicorn лимит в приложении до 3 раз выше номинала. Номинал занижен до 5 попыток в минуту, строгий лимит ставит nginx в шаге 2. Оговорка записана в `ARCHITECTURE.md`, раздел 10. |
| `/schema/` и `/docs/` для lead в prod отложены на шаг 13 | Решение принято вместе с пользователем, чтобы шаг 3 остался в рамках плана. Сейчас они открыты только при `DEBUG`. Нужны permission `IsLead` и CSP для Swagger UI; пункт добавлен в шаг 13, `ARCHITECTURE.md` и комментарий в `config/urls.py` приведены в соответствие. |
| Шаг 4: эндпоинт истории и фильтры без отдельных коммитов | В плане шага 4 были отдельные коммиты для фильтров и `GET /tasks/{id}/events/`. Фильтры подключены в том же `ViewSet`, поэтому они вошли в один коммит `feat(tasks): add task API with filters, pagination and events`. Содержание шага не изменилось. |
| Шаг 5: `submit` без проверки вложения | ARCHITECTURE §7 требует вложение текущего раунда, но `TaskAttachment` создаётся в шаге 6. Проверка и тест «submit без вложения» (они уже есть в плане шага 6) добавляются там; в коде стоит `TODO(step 6)`, в `ARCHITECTURE.md` пометка. Исключение только для роли creative, тело фиксированное и без данных задачи; записано в `ARCHITECTURE.md`, раздел 9. Цена: креативщик перебором id отличает существующую задачу от несуществующей. |
